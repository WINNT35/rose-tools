Contributing

Rose Tools welcomes contributions from the community. This page provides a brief overview of the project structure, coding standards, and licensing requirements for contributors.

Build Requirements

  • MinGW (GCC for Windows)
  • C89 compatible compiler
  • make (for make all)
  • Windows XP or ReactOS (for testing)
  • Wine or a Windows machine (for make test; separate from the main build)

Coding Standards

The preferred standard for Rose Tools is C89, particularly for the outer ring. This ensures compatibility with older toolchains and keeps the codebase consistent with the project's targets. Contributions should follow C89 where practical:

  • Prefer /* */ block comments over //
  • Declare variables at the top of a block where possible
  • No GLib or other Unix-specific dependencies
  • Win32 API only for platform-specific code

Project Structure

Rose Tools is divided into several directories:

  • lib/ — the core; contains the guest protocol implementation and shared libraries. This layer is heavily derived from open-vm-tools and should be modified as little as possible. Changes here should only be made where strictly necessary for Windows NT compatibility.
  • services/ — the outer ring; contains the daemon, utilities, and plugins. This is where the majority of new development takes place. New features should be implemented as plugins under services/plugins/ wherever possible. Note that some files in this layer are closely derived from open-vm-tools and carry dual attribution; always check the license header of the individual file.
  • tests/ — testing infrastructure. Buildable with make test and runnable on Wine or Windows.
  • help/ — user documentation.
  • docs/ — developer documentation covering architecture, keywords, and plugin development. Recommended reading before contributing.

When in doubt, ask yourself whether your code belongs to the protocol and core infrastructure (lib/) or to the services and tools built on top of it (services/). Keep the two layers cleanly separated.

Writing a Plugin

New features should be implemented as plugins loaded dynamically by vmrosd.exe at startup rather than standalone executables or modifications to the daemon itself. A plugin is a DLL that exports a single entry point, RoseOnLoad, which receives the application context and registers any TCLO handlers the plugin needs. Plugins can read their own configuration from tools.conf via a dedicated section. Place the compiled DLL in plugins\vmsvc\ and it will be loaded automatically on next startup. Refer to the existing guestInfo plugin as a reference implementation, and see docs/ for detailed notes on the plugin architecture and API.

Licensing

All contributions must use the correct license for their layer. The license structure is nuanced; always check the license header of the individual file as the authoritative source. The general breakdown is:

  • lib/ — GNU Lesser General Public License v2.1 only
  • services/ — GNU General Public License v2.0 or later; files sufficiently derivative of open-vm-tools carry dual attribution and are licensed under LGPL v2.1 only instead
  • tests/ — GNU General Public License v2.0 or later
  • help/ — MIT License

Every source file must include the appropriate license header. See existing files for the correct header format. If in doubt, refer to the COPYING file in the relevant directory and the License page.

Getting Involved

Bug reports, feature requests, and pull requests are welcome on the GitHub repository. When submitting a bug report please include your VMware version, hardware compatibility mode, and the exact output or error message you received.
